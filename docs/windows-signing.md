# Подпись Windows-сборки

> Короткий ответ: `proxy_dom.exe` и MSI нужно подписать сертификатом
> code signing от удостоверяющего центра, который входит в
> [Microsoft Trusted Root Program](https://learn.microsoft.com/security/trusted-root/program-requirements).
> Сборка к этому готова: `build-msi.ps1 -Signing require`.

---

## 1. Почему без сертификата не запускается

На скриншоте — не антивирус и не SmartScreen, а **Интеллектуальное управление
приложениями** (Smart App Control, SAC). Это механизм Windows 11, который
разрешает запуск файла, только если выполнено одно из двух:

- приложение уже известно службе оценки Microsoft;
- файл подписан сертификатом УЦ из Microsoft Trusted Root Program.

Неподписанный `proxy_dom.exe` не проходит ни по одному условию, поэтому
появляется «Издатель не проверен… не удалось проверить издателя». MSI
блокируется так же, только на шаг раньше — при установке.

Два разных механизма, которые легко перепутать:

| Механизм | Где | Что проверяет | Лечится сертификатом |
|---|---|---|---|
| **Smart App Control** | Windows 11, включён на новой установке | подпись и репутацию **до запуска** | да, если УЦ в программе доверия |
| **SmartScreen** | все версии Windows | репутацию файла и издателя **при скачивании** | частично: имя издателя появляется сразу, предупреждение уходит по мере репутации |

У SAC нет списка исключений для пользователя: либо приложение подписано, либо
его выключают в настройках. Выключение необратимо — включить обратно можно
только переустановкой Windows, поэтому просить об этом пользователей — плохой
путь. Подпись — единственный способ, который не требует от человека менять
настройки безопасности.

## 2. Что сертификат даёт, а что нет

Даёт:

- запуск под SAC на Windows 11 (при цепочке до доверенного корня);
- имя издателя в UAC вместо «Неизвестный издатель»;
- имя издателя в SmartScreen и накопление репутации от версии к версии —
  подпись одним и тем же сертификатом переносит доверие на новые файлы,
  неподписанные начинают с нуля каждый релиз;
- меньше поводов для эвристики антивирусов: подписанный файл с внятными
  метаданными выглядит иначе, чем безымянный exe из временной папки.

Не даёт:

- **мгновенного отсутствия предупреждений SmartScreen.** С 2024 года даже EV
  не даёт мгновенной репутации: первые скачивания нового файла всё равно могут
  показать предупреждение. Платить за EV ради SmartScreen смысла нет;
- **иммунитета от антивирусов.** TUN-драйвер, служба и перехват трафика — это
  поведение, которое эвристика проверяет независимо от подписи. Ложные
  срабатывания отправляются в Microsoft через
  [WDSI](https://www.microsoft.com/wdsi/filesubmission) и вендорам антивирусов;
- **работы самоподписанного сертификата.** Он годится только для проверки
  скриптов: Windows не доверяет ему, пока его не установят в корневые на каждой
  машине, а установка корневого сертификата требует интерактивного
  подтверждения. Сборка такой сертификат отвергает на шаге проверки.

Отдельно про срок жизни подписи: сертификат живёт год-два, установленная копия
приложения — дольше. Поэтому подпись ставится с **меткой времени (RFC 3161)**:
Windows проверяет, что на момент подписания сертификат был действителен.
Скрипт делает это всегда; у Azure Artifact Signing сертификаты живут три дня,
и без метки времени подпись перестаёт проверяться почти сразу. Метка ставится
по сети, поэтому сборка релиза требует доступа к серверу метки времени
(`timestamp.digicert.com` или `timestamp.acs.microsoft.com`).

## 3. Какой сертификат брать

| Вариант | Цена | Ключ | Комментарий |
|---|---|---|---|
| **Azure Artifact Signing** (бывший Trusted Signing) | ~$9.99/мес | в HSM Microsoft | Проще всего для автоматизации: нет токена, подпись по сети. Организации — США, Канада, ЕС, Великобритания, Австралия, Новая Зеландия, Япония, Корея, Сингапур, Швейцария, Норвегия, Израиль; частные лица — США и Канада. Идентичность проверяет Microsoft, это несколько рабочих дней |
| **OV-сертификат** УЦ (DigiCert, Sectigo, Certum, SSL.com…) | $150–300/год | USB-токен или облачный HSM | Универсальный вариант. С июня 2023 CA/Browser Forum требует хранить ключ на HSM, поэтому «просто pfx» новые УЦ не выдают: будет токен или облако |
| **EV-сертификат** | $400+/год | токен/HSM | С 2024 года не даёт преимуществ в SmartScreen. Нужен, только если его требует закупка или корпоративный заказчик |
| **Бесплатные программы для open source** (SignPath Foundation, Certum Open Source) | 0 | у фонда/УЦ | Проект MIT и публичный, поэтому формально подходит. Но издателем в подписи будет фонд, а не «Proxy Dom», и условия у них свои — читать перед подачей |
| **Самоподписанный** | 0 | локально | Только для проверки скриптов и тестового контура. Для распространения не годится |

Что важно знать до покупки:

- **Сертификат — юридический шаг, а не технический.** УЦ проверяет личность:
  организацию (ООО, ИП) или физлицо по паспорту. В сертификате будет то имя,
  которое увидит пользователь в UAC, поэтому оно должно совпадать с брендом или
  названием юрлица.
- **Проверьте УЦ в списке доверия Microsoft.** Актуальный список — отчёт CCADB,
  на который ссылается Microsoft:
  <https://ccadb.my.salesforce-sites.com/microsoft/IncludedCACertificateReportForMSFT>.
  Сертификат УЦ вне этого списка даёт ровно тот же диалог, что на скриншоте,
  только уже с подписью.
- **Российские УЦ в программе доверия Microsoft не участвуют**, а Azure Artifact
  Signing недоступен для организаций и частных лиц из России: список регионов
  выше. Национальные сертификаты подписи кода, о которых пишут в 2026-м, в
  программу пока не входят — если это изменится, проверять по тому же отчёту
  CCADB. Практический вывод: у варианта должен быть УЦ, работающий с вашей
  юрисдикцией; техническая часть сборки от этого не зависит.

### Если юрлицо в Казахстане

Казахстан не входит в регионы Azure Artifact Signing, поэтому облачная подпись
Microsoft отпадает. Остаётся классический OV-сертификат на ТОО — и это лучший
вариант: издателем в UAC будет название компании, совпадающее с футером сайта,
а не чужой фонд.

Ориентиры на октябрь 2026; цены и курсы проверять у продавца:

| Вариант | Цена | Ключ | Где брать |
|---|---|---|---|
| **Certum Standard Code Signing** (OV, облако) | ~€70–150/год | SimplySign, без токена | Certum напрямую или реселлер для Центральной Азии (aHOST) |
| **DigiCert Code Signing** (OV) | 226 440 ₸/год | KeyLocker или токен | onehost.kz, есть офис в Павлодаре |
| **SSL.com OV + eSigner** | ~$200–300/год | облако | ssl.com напрямую |

EV не нужен: с 2024 года он не даёт преимуществ в SmartScreen.

Что попросят на проверку:

- документы ТОО: справка о государственной регистрации с БИН, устав, адрес;
- рабочий телефон из реестра — УЦ звонит и проверяет, что компания отвечает;
- подтверждение контроля над доменом сайта (письмо на адрес в домене или
  DNS-запись);
- паспорт директора или подписанта.

Срок — от двух до десяти рабочих дней. Проверка идёт по официальным реестрам
Казахстана, поэтому название в заявке должно совпадать с реестром.

Издатель в подписи — юрлицо латиницей (`UMIKUM TOO` или то, как транслитерирует
УЦ). В свойствах файла останется «Proxy Dom»: это нормально, но в релиз-нотах
стоит написать, что издатель — ТОО «УМИКУМ», иначе пользователь увидит
незнакомое имя.

Ключ в облаке удобнее токена: токен едет почтой и его не подключить к раннеру
CI, а Certum SimplySign и DigiCert KeyLocker ставят на машину виртуальный
смарт-карточный провайдер — сертификат появляется в хранилище Windows, и
`PROXYDOM_SIGN_THUMBPRINT` работает без изменений.

Если провайдер не даёт Windows-клиента с KSP (например, SSL.com eSigner), для CI
понадобится отдельная интеграция через его REST/CLI — как у Azure Artifact
Signing в `signing.ps1`.

## 4. Как включить подпись

Поддерживаются три идентичности. Скрипт выбирает ту, для которой заданы
переменные; если заданы две сразу — останавливается и просит выбрать явно.

### Сертификат в хранилище Windows (токен или HSM)

```powershell
# отпечаток виден в certmgr.msc, вкладка "Состав" -> "Отпечаток"
$env:PROXYDOM_SIGN_THUMBPRINT = "A1B2C3..."
.\build-msi.ps1 -Version 1.1.0 -Signing require
```

Токен должен быть подключён; если приватного ключа нет, скрипт скажет об этом
до начала сборки, а не в середине.

### PFX-файл (тестовый контур, старые сертификаты)

```powershell
$env:PROXYDOM_SIGN_PFX_PATH = "C:\certs\proxydom.pfx"
$env:PROXYDOM_SIGN_PFX_PASSWORD = "..."
.\build-msi.ps1 -Version 1.1.0 -Signing require
```

### Azure Artifact Signing

```powershell
winget install -e --id Microsoft.Azure.ArtifactSigningClientTools
az login

$env:PROXYDOM_ARTIFACT_SIGNING_ENDPOINT = "https://plc.codesigning.azure.net"  # регион аккаунта
$env:PROXYDOM_ARTIFACT_SIGNING_ACCOUNT  = "proxydom-signing"
$env:PROXYDOM_ARTIFACT_SIGNING_PROFILE  = "proxydom-public"
$env:PROXYDOM_ARTIFACT_SIGNING_DLIB     = "C:\Tools\Azure.CodeSigning.Dlib.dll"
.\build-msi.ps1 -Version 1.1.0 -Signing require
```

Точный путь к `Azure.CodeSigning.Dlib.dll` зависит от способа установки: найдите
этот файл в папке Artifact Signing Client Tools (или в распакованном NuGet-пакете
`Microsoft.ArtifactSigning.Client`, каталог `bin\x64`) и укажите его в переменной.

### Общие переменные

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `PROXYDOM_SIGN_TIMESTAMP_URL` | DigiCert / `timestamp.acs.microsoft.com` для Artifact Signing | своя метка времени |
| `PROXYDOM_SIGN_EXPECTED_SUBJECT` | — | требует, чтобы подписал именно этот издатель; страховка от чужого сертификата в хранилище |
| `PROXYDOM_SIGNTOOL` | ищется в Windows SDK | нестандартная установка SDK |

### Что именно подписывается

Перед упаковкой в MSI: все `.exe` и `.dll` в корне payload, у которых нет
валидной подписи, — окно `proxy_dom.exe`, движок туннеля `proxydom-engine.exe`,
служба, контроллер и DLL плагинов Flutter (`flutter_windows.dll`,
`app_links_plugin.dll`, `rive_native.dll` и т. п.). `wintun.dll` не трогается —
это бинарник WireGuard, и подменять его издателя нельзя. Файлы, у которых уже
есть валидная подпись (Microsoft, WireGuard), остаются как есть:
`-SkipAlreadySigned`.

Порядок важен: payload подписывается **до** WiX, потому что MSI фиксирует файлы,
которые упаковывает; сам MSI — **после** сборки.

Режимы:

| `-Signing` | Поведение |
|---|---|
| `auto` (по умолчанию) | подписывает, если сертификат настроен; иначе предупреждает и собирает неподписанный MSI |
| `require` | без сертификата сборка падает; так собираются релизы |
| `off` | не подписывает и не предупреждает; для локальных экспериментов |

Если сертификат есть, но цепочку Windows не принимает (самоподписанный,
просроченный, УЦ вне программы доверия), сборка падает на проверке
`signtool verify /pa` — а не выпускает файл, который выглядит подписанным.

### Без полной сборки

```powershell
.\sign.ps1 -Path .\out\ProxyDom-1.1.0.msi
```

Подпишет и проверит уже готовый файл теми же функциями, что и сборка.

## 5. Как проверить результат

```powershell
Get-AuthenticodeSignature .\out\ProxyDom-1.1.0.msi | Format-List Status, SignerCertificate
```

Ожидается `Status: Valid` и `CN=` вашего издателя. Дополнительно — та же
проверка, которой Windows решает, доверять ли файлу:

```powershell
$signtool = Get-ChildItem "${env:ProgramFiles(x86)}\Windows Kits\10\bin\*\x64\signtool.exe" |
    Sort-Object FullName -Descending | Select-Object -First 1
& $signtool.FullName verify /pa /v .\out\ProxyDom-1.1.0.msi
```

Проверять нужно на **чистой Windows 11 с включённым Smart App Control**:
установить MSI, запустить, посмотреть, что в UAC стоит имя издателя, и что
приложение стартует без диалога. Зелёная проверка в CI этого не заменяет.

## 6. CI

Сейчас в CI Windows собирает службу и гоняет тесты, а MSI собирается локально
(см. `AGENTS.md`, §5). Для подписи в CI понадобятся секреты репозитория:

| Секрет репозитория | Куда попадает |
|---|---|
| `PROXYDOM_SIGN_PFX_BASE64` | workflow декодирует его в файл и выставляет `PROXYDOM_SIGN_PFX_PATH` |
| `PROXYDOM_SIGN_PFX_PASSWORD` | `PROXYDOM_SIGN_PFX_PASSWORD` |
| `PROXYDOM_SIGN_THUMBPRINT` | `PROXYDOM_SIGN_THUMBPRINT`, если сертификат ставится на раннер |

Для Azure Artifact Signing секреты не нужны: вход по OIDC в Azure, дальше
[`azure/artifact-signing-action`](https://github.com/azure/artifact-signing-action)
или тот же `signtool` с dlib. Отдельная джоба сборки MSI появится вместе с
задачей на CI-релиз Windows; сам скрипт подписи от неё не зависит.

Что уже проверяется в CI: `windows-service.yml`, джоба **Signing self-test** —
подписывает настоящий PE одноразовым сертификатом, проверяет, что подпись
читается, что изменение байта её ломает, и что самоподписанный сертификат
отвергается проверкой.

## 7. Если диалог уже появился у пользователя

Пока подписанной сборки нет, вариантов два:

1. **Выключить Smart App Control**: Параметры → Конфиденциальность и защита →
   Безопасность Windows → Управление приложениями и браузером → Smart App
   Control → Выкл. Обратно включить нельзя без переустановки Windows.
2. **Ждать подписанную сборку.** Это единственный вариант, который не просит
   человека ослаблять защиту.

Для MSI, скачанного из интернета, SmartScreen покажет «Windows защитила ваш
компьютер»: «Подробнее» → «Выполнить в любом случае». Это не ошибка установщика,
а отсутствие репутации у нового файла; после подписи там появится имя издателя.

Не советуйте отключать антивирус целиком и не просите добавлять папку в
исключения — это лечит симптом и создаёт привычку, которая однажды сработает
против пользователя.

---

## 8. Чек-лист релиза

- [ ] сертификат выпущен, не истёк, УЦ есть в списке доверия Microsoft;
- [ ] сборка запущена с `-Signing require`;
- [ ] `Get-AuthenticodeSignature` на MSI и на exe — `Valid`;
- [ ] установка и запуск проверены на чистой Windows 11 с включённым SAC;
- [ ] ложные срабатывания антивирусов отправлены в WDSI и вендорам;
- [ ] следующий релиз подписан тем же сертификатом — иначе репутация начинается
      заново.
